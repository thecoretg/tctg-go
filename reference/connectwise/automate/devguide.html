Base URL

All Automate REST endpoints will be appended to your Automate server's FQDN (Fully Qualified Domain Name).

  • https://companyABC.hostedrmm.com/cwa/api/v1/apitoken
  • https://connectwise.compayABC.com/cwa/api/v1/computers

Client ID

Starting with 2020.11, all integrations must have a registered clientId with the Developer Network. Integrations will be required to use these going forward for all API communication.

Refer to clientId documentation for more information and to apply one.

Implementation

The clientId is implemented through an HTTP header in the API Request.  If you are working with a tool that lets you set your own headers, such as Postman, you would simply add the header key of clientId and a value of the unique GUID that is provided.

Authentication

The Automate APIs use a Bearer token authentication scheme to authenticate every user request for the API. Until the release of Automate version 25.0.2.11, the Automate APIs only accepted tokens issued by the native Automate instance for authentication purposes. Learn more about using SSO Tokens here.

Bearer Token

Note: SSL/HTTPS is required

Tokens are available by POSTing to /cwa/api/v1/apitoken with an Automate username and password, like below:

Header

NOTE: This client ID is only an example. You should replace the actual ID with your assigned client ID.

Content-Type: application/json
ClientID: 4f2aa08e-9bed-43d5-ad08-c366d8ab6ddd

 

Body
view sourceprint?
1{
2"Username":"Admin",
3"Password":"VknMChjykbikug"
4}

Bearer Token Refresh

All tokens expire after 1 hour. However, you can POST a token to the refresh endpoint to extend your time before resubmitting credentials. When the first token is issued, you are provided an AbsoluteExpirationDate. This is 24 hours from creation in UTC. You can refresh this session as many times as you'd like within that 24 hours, but once the AbsoluteExpirationDate expires, a new token must be created using the APIToken endpoint. Each refresh response will contain a new token for those 24 hours.

Note: The timestamps returned are provided in UTC time to ensure consistent timekeeping across different systems. You may need to convert it to your local time zone if necessary.

The refresh endpoint is: /cwa/api/v1/apitoken/refresh 

Header

NOTE: This clientID is only an example. You would replace the actual ID with your assigned client ID.

Content-Type: application/json
ClientID: 4f2aa08e-9bed-43d5-ad08-c366d8ab6ddd

Body

The body will just contain your token in quotes, like below:

view sourceprint?
1"5Ywol5E3s0+nTeLhgcP5GA=="

Response

The key portion of this response is the AccessToken, which will replace the one you submitted with your POST.

The AbsoluteExpirationDate will not update or change. Your session is still timed against the initial AbsoluteExpirationDate issued at the initial token request.

SSO Token

Starting from Build 25.0.2.111, the Automate APIs can authenticate API requests with both the Automate native token and the ConnectWise SSO token when passed as a bearer token in the authentication header of the API request.

Requirements

The Automate instance must have SSO authentication enabled. The user who wants to authenticate an API request via an SSO token must be registered as an SSO user for that Automate instance, along with the corresponding Automate permissions.

Limitations

This authentication mechanism applies to all API requests except Auth/Token issuing APIs. It has the following limitations:

  1. It cannot log the last successful/unsuccessful login attempt of the user.
  2. Two-factor authentication is not applicable.
  3. No access-related updates are made to any newly added agents that were not added by the user and do have permission to show on the web for the user's client. The user must log in to the Automate application to have all access-related updates.
  4. The token expiration time is the same as the SSO token expiration time.

Multi-Factor Authentication

Beginning with ConnectWise Automate version 2020.1, multi-factor authentication (MFA) is enabled by default for all non-SSO user accounts. More information on this change can be found here: Multi-Factor Authentication for Automate

If two-factor authentication is enabled on the Automate user, you will also need to addTwoFactorPasscode, like below:

Bypass Default MFA for Integrator Users

For integrations that make API calls to function properly with Automate, we recommend bypassing the default MFA for the user account because the integration cannot receive and respond with an authentication token. Bypassing the default MFA does not affect integrations such as DUO or Google Authenticator. An audit action and entry in the User Settings table are recorded. At this time, there is no global setting to bypass MFA. 

To bypass default MFA for an integrator user:

  1. In the Control Center, navigate to System > Users and Contacts > Users and double-click on an integrator user
  2. Select the Integrator checkbox
  3. Click Save.
  4. We recommend clicking on the Permissions tab to verify that the integrator user account is assigned limited permissions. 
  5. Save any changes. 

Formatting Each Method

GET

Get requests are used for finding individual records and a list of records. To grab an individual entity, you must specify an ID within the request URL.

/cwa/api/v1/computers/1

When requesting a grouping of records, do not include an id record.  Optionally include parameters at the URL's end to grab a specific set of records.

/cwa/api/v1/computers?condition=(id >= 1 and id <= 10)

When looking at an endpoint, the parameters section will tell you which fields can be used to filter the request.  In addition to the below parameters, you can use the Fields and Columns to manipulate the response dataset.

URL Max Length

The HTTP standards document does not impost a max URL length.  However, various browsers and applications have different limits in place.  In addition, search engines favor URLs that are around 2000 characters.  As a URL grows in length, it no longer remains user-friendly and becomes unusable or readable by users.  This causes issues with troubleshooting and leads to confusion.  We recommend keeping the URL length of each request to a maximum of 2000 characters.  This will ensure there are no compatibility issues with various servers and configurations.  Please remember that the maximum length of a domain name can reach 255 characters.  With that in mind, the safe max length of a URL would be around 1745 characters.  

Query String Parameters

NOTE: Query keys are case-insensitive.

Query Parameter Description Example
PageSize Controls the size of pages returned in the response

/cwa/api/v1/computers?pagesize=25
Page Use to page the results returned in the response /cwa/api/v1/computers?page=2
OrderBy Used to sort your results by a fieldname /cwa/api/v1/computers?orderby=fieldname asc/desc
Multiple Query Syntax Use an & to denote a second Query Syntax /cwa/api/v1/groups?ids=1177&includefields=id
IncludeFields Specifies a list of fields to be included in the response /cwa/api/v1/computers?includefields=id,name,location
Ids Used to specify a list of object ids /cwa/api/v1/computers?ids=1,2,3,4
Expand Grabs entire child object instead of name and id /cwa/api/v1/computers?expand=client,location
ExcludeFields Specifies a list of fields to be excluded in the response /cwa/api/v1/user?excludefields=image
Condition Used as search parameters to filter results /cwa/api/v1/computers?condition=operatingSystemName contains 'Windows'
PageSize

Controls the size of pages returned in the response.  Default pageSize=50 max=1000.

Example:

/cwa/api/v1/computers?pagesize=25

Page

Use to page the results returned in the response. The index starts at 1.

Example:

/cwa/api/v1/computers?page=2
 

OrderBy

Used to sort the results by a field. Can be sorted in ascending or descending order.

Examples:

/cwa/api/v1/computers?orderby=fieldname asc
/cwa/api/v1/computers?orderby=fieldname desc

Multiple Query Syntax

Use an ampersand between conditions.

Examples:

/cwa/api/v1/groups?ids=1177&includefields=id
/cwa/api/v1/groups?expand=Contacts&includefields=id,Contacts,name

IncludeFields

Used to specify a list of fields to include in the response.

Example:

/cwa/api/v1/computers?includefields=id,name,location

ExcludeFields

Used to specify a list of fields to exclude from the response. This is ignored if the 'IncludeFields' parameter is also specified.

Example:

/cwa/api/v1/user?excludefields=image

Ids

Used to specify a list of object ids.

Example:

/cwa/api/v1/computers?ids=1,2,3,4

Expand

By default, child objects only return the 'id' and 'name' fields in the response. 'expand' returns the entire child object. If the field expanded is an array of child objects, the parameters 'page', 'pageSize', 'orderby', 'condition', 'includefields', and 'excludefields' can be used as sub-parameters.

Examples:

/cwa/api/v1/computers?expand=client
/cwa/api/v1/computers?expand=client,location
/cwa/api/v1/computers?expand=tickets(page=1;pagesize=25;condition=statusName eq 'Open')

Condition

Used to specify a condition to the query. Supported operators are '=', '!=', 'eq', '>', '>=', '<', '<=', 'and', 'or', '()', 'like', 'contains', 'in', 'not'. The 'not' operator only uses 'in', 'like', or 'contains'. The '=' and 'eq' operators are the same. Either single or double quotes can surround string values. Boolean values are specified as 'true' or 'false'. Parenthesis can only be used to control the order of operations and group conditions. The 'like' operator translates to the MySQL 'like' operator.

Field names are case insensitive. Field names can also have depth and reference to child objects. Child objects are referenced with the '.' operator (EX: locations.name).

Examples:

/cwa/api/v1/computers?condition=id=1
/cwa/api/v1/computers?condition=id!=1
/cwa/api/v1/computers?condition=id eq 1
/cwa/api/v1/computers?condition=operatingSystemName contains 'Windows'
/cwa/api/v1/computers?condition=(id >= 1 and id <= 10) and (location.name eq 'LocationA' or location.name eq 'LocationB')
/cwa/api/v1/computers?condition=id in(1, 2, 3)

POST

Post is used when creating new records. The body of the request must be sent in JSON format. When sending a Post, the response body will include the newly created record ID as well as a Get request for the record. If you pass a post request without filling out every possible value, the system will attempt to default all required information, and anything that does not require a value will be set to Null.

DELETE

Delete requests are used to remove records from the ConnectWise Automate system. Please take care when removing items, as they cannot be recovered. The record's ID needs to be included in the request URL.

Example:

/cwa/api/v1/computers/3/alerts/10

PATCH

Patch requests enable the ability to update individual fields on an entity.  When formatting the request you can specify multiple fields to be updated.  When working with a patch, the entire object is part of an array and must be surrounded by square brackets, as per the example below.  You will run into errors if you do not have the square brackets.  In addition, when you are updating a reference, you can only update it through the use of unique values.  Many times, a Name is not considered unique.

Examples:

/cwa/api/v1/computers/3/

Body:
[
    {"op": "replace", "path": "location/iD", "value": "15"}

 ]

PUT

Put requests are designed to replace an entity completely.  They work like a Post request, except that you must specify an already created entity in your URL.  When you use Put to update a record, any field that has not been specified will be overridden with the system defaults or set to Null.

 

Troubleshooting

Log Location

On the Automate Server -- C:\Windows\Temp\_AutomateLogs

To Enable Verbose Logging

  1. Navigate to C:\inetpub\wwwroot\cwa
  2. Edit the web.config file with Notepad
  3. Find the line <add key="serilog:minimum-level" value="Information"/>
  4. Change "Information" to "Verbose"
  5. Once you have gathered the logs you need, go back to the web.config file and change "Verbose" back to "Information" 

Notes

  • All log entries will begin with the following
    1. Timestamp including timezone offset (i.e., 2017-10-13 10:28:08.489 -04:00)
      • Keep in mind that this is the web server's system time
    2. Log level in brackets (i.e. [Error])
      • Levels ordered from least to most severe are...
        • Verbose
        • Debug
        • Information
        • Warning
        • Error
        • Fatal
    3. THREAD_ID (i.e. THREAD_ID=54)
    4. API_VERSION (i.e. API_VERSION=12.0.0.210GA)
       
  • Non-Exception related entries will typically begin with a brief message followed by searchable key/value pairs
  • Searchable key/value pairs are written in this format "KEY_NAME="Value name""
  • Log entries use a line of stars as a delimiter for readability (i.e. ************************************)
